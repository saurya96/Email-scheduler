# ReachInbox email scheduler

A TypeScript monorepo for a persistent email scheduling dashboard. The dashboard supports Google OAuth and email/password accounts; the API stores each recipient's email in PostgreSQL, schedules jobs with BullMQ/Redis, and sends through configured Ethereal SMTP accounts. Elasticsearch powers email search, and Slack incoming-webhook OAuth can notify a connected channel when a sender reaches its hourly cap.

## Requirements

- Node.js 20+
- Docker and Docker Compose
- Optional Google OAuth web client credentials (email/password sign-in works without them)
- Optional Slack app with `incoming-webhook` OAuth scope
- Ethereal account(s), generated by the helper below

## Run locally

1. Copy `backend/.env.example` to `backend/.env` and set `SESSION_SECRET` to a random value of at least 32 characters and `TOKEN_ENCRYPTION_KEY` to 64 hexadecimal characters. For example, generate them with `openssl rand -base64 32` and `openssl rand -hex 32`.
2. Create an Ethereal test account and paste the printed sender object into the `SMTP_SENDERS` JSON array in `backend/.env`:

   ```sh
   npm install
   npm run ethereal
   ```

3. To enable Google sign-in, add a Google OAuth client ID and secret to `backend/.env`. Register `http://localhost:4000/auth/google/callback` as an authorized redirect URI. Add `http://localhost:5173` as an authorized JavaScript origin. Email/password registration does not require Google credentials.
4. Optionally create a Slack app with the `incoming-webhook` OAuth scope. Set its redirect URI to `http://localhost:4000/auth/slack/callback`, then set `SLACK_CLIENT_ID` and `SLACK_CLIENT_SECRET` in the backend environment. The user chooses the channel during Slack's OAuth installation.
5. Start PostgreSQL, Redis, and Elasticsearch:

   ```sh
   docker compose up -d
   ```

6. Apply the database schema and start the API, worker, and frontend in three development processes:

   ```sh
   npm run db:generate
   npm run db:migrate --workspace backend -- --name init
   npm run dev
   ```

7. Open [http://localhost:5173](http://localhost:5173). Create an email/password account or sign in with Google. Email/password accounts require a password of at least 10 characters. The API is at `http://localhost:4000`; the authenticated BullMQ dashboard is at `http://localhost:4000/admin/queues`.

The frontend optionally reads `VITE_API_URL` from `frontend/.env` (see `frontend/.env.example`). Defaults are suitable for local development.

## Environment

See [`backend/.env.example`](./backend/.env.example). Important scheduler settings:

| Variable | Default | Description |
| --- | ---: | --- |
| `WORKER_CONCURRENCY` | `5` | Number of concurrent BullMQ processors per worker process. |
| `MIN_SEND_DELAY_MS` | `2000` | Minimum gap between all SMTP send reservations, shared across worker instances via Redis. |
| `MAX_EMAILS_PER_HOUR_PER_SENDER` | `200` | Hard hourly cap for each SMTP sender, shared across tenants. Each tenant can set a lower sender cap when composing. |
| `SMTP_SENDERS` | — | JSON array of SMTP sender objects. Add multiple Ethereal accounts to rotate senders across recipients. |
| `EMAIL_ATTACHMENT_STORAGE_DIR` | `./data/email-attachments` | Private directory for AES-256-GCM encrypted attachment files. The API and worker must share the same persistent directory. |
| `EMAIL_ATTACHMENT_MAX_FILE_SIZE_MB` | `10` | Maximum size of one attachment, configurable up to 25 MB. |
| `EMAIL_ATTACHMENT_MAX_TOTAL_SIZE_MB` | `20` | Maximum combined size of attachments per email batch, configurable up to 50 MB. |

Compose settings can request a longer inter-email delay or a lower hourly limit; they cannot exceed the configured server-side hourly maximum. Each scheduled recipient is a separate persistent email record and BullMQ job.

## Architecture and guarantees

- **Durable scheduling:** PostgreSQL is the source of truth for email content, status, and schedule time. BullMQ delayed jobs are stored in Redis with AOF persistence enabled by the Compose stack. On worker startup, all still-scheduled database rows are reconciled into the queue, using the database email ID as the stable BullMQ job ID. Restarting the API or worker does not reset schedules.
- **Idempotency:** The scheduling API requires an `Idempotency-Key` header and uses a unique database key per recipient. The dashboard retains its key while a compose action is active. BullMQ job IDs are stable email IDs, so concurrent API/worker reconciliation cannot create additional active jobs for an email.
- **Attachments:** Compose requests use authenticated multipart uploads and allow up to five PDF, DOC, DOCX, PNG, JPG/JPEG, GIF, WEBP, SVG, TXT, CSV, XLS, or XLSX files. The backend checks declared MIME types and file signatures/content, sanitizes SVG, then encrypts each file with AES-256-GCM in the private `EMAIL_ATTACHMENT_STORAGE_DIR`; PostgreSQL stores opaque references and metadata only. The worker decrypts and attaches files at delivery time, while authenticated tenant-scoped routes provide previews and downloads. Configure a persistent shared volume at the same path for API and worker processes so scheduled jobs retain access across restarts. Per-file and combined limits are configurable with the environment variables above.
- **Rich text:** The compose editor supports common inline formatting, lists, and alignment. The API sanitizes the allowed HTML tags and alignment styles before storing and sending the message.
- **Delivery boundary:** SMTP does not provide a transactional exactly-once protocol. The worker claims a record in PostgreSQL before sending, uses a stable `Message-ID`, and recovers stale `SENDING` records after a ten-minute lease. A crash after SMTP accepted a message but before PostgreSQL recorded `SENT` can still cause a duplicate on recovery; the design makes that unavoidable ambiguity explicit rather than claiming impossible exactly-once delivery.
- **Concurrency and pacing:** Each worker's concurrency is configurable. Before sending, a Redis Lua script atomically checks both the tenant/sender hourly cap and the shared sender cap, then reserves a global next-send timestamp. This coordinates limits and the minimum send gap across multiple worker processes. When a quota or gap is not available, BullMQ moves that same active job into the delayed state; jobs are not dropped. Compose requests accept up to 10,000 unique recipients and are persisted/indexed in bounded batches.
- **Hourly limits:** Counters are keyed by UTC hour, tenant, and sender, plus a shared sender counter capped by `MAX_EMAILS_PER_HOUR_PER_SENDER`. Reaching either cap defers the job to the next UTC hour. A Redis `SET NX` key ensures Slack is notified only once per tenant/sender/hour (and released if the webhook request fails so another rate-limited job can retry the alert). Without a Slack connection, email scheduling continues normally.
- **Search:** Email records are indexed in Elasticsearch at schedule and after delivery. Search is tenant-filtered and supports recipient, subject, and body matches; PostgreSQL remains the authority for displayed status.
- **Queue visibility:** Bull Board is mounted at `/admin/queues` and protected by the same authenticated session as the API.
- **Authentication and credentials:** Google OAuth uses authorization code exchange, ID-token verification, state validation, and an HTTP-only session cookie backed by Redis. Email/password accounts use scrypt password hashes, per-IP/email login throttling, and the same session mechanism. Slack webhook URLs are AES-256-GCM encrypted in PostgreSQL using `TOKEN_ENCRYPTION_KEY`. OAuth credentials and SMTP passwords are only read from environment configuration.

## Implemented assignment features

### Backend

- Express TypeScript API for email scheduling, account/session information, and scheduled/sent lists.
- PostgreSQL/Prisma persistence; queue restoration from stored jobs after restarts.
- BullMQ delayed jobs, configurable worker concurrency, Redis-backed distributed pacing and per-sender hourly caps.
- Ethereal SMTP sending, configurable multiple sender accounts, retry handling, and stable message IDs.
- Elasticsearch indexing and tenant-scoped email search.
- Authenticated Bull Board queue dashboard.
- Real Google and email/password sign-in, and Slack incoming-webhook OAuth connect/disconnect, with live rate-limit notifications.

### Frontend

- Google and email/password sign-in, email account registration, and user profile/logout controls.
- Inbox-inspired responsive workspace based on the supplied reference: sidebar, scheduled/sent navigation, search, queue monitor, and email tables.
- Compose form with recipient chips, CSV/text parsing, up to five file attachments, subject/body, immediate send, quick scheduled-send times, delay, and hourly limit.
- Email details, persistent star/unstar, and cancellation of emails that are still scheduled.
- Loading, empty, error toast, status, and refresh states.
- Search results and inbox lists are paginated in 100-email batches for large schedules.

## Notes and trade-offs

- The demo uses Ethereal's fake SMTP; it does not deliver messages to real recipients. Ethereal preview URLs are logged by the worker.
- Elasticsearch and PostgreSQL are separate services; a database commit and an Elasticsearch write cannot be atomic. PostgreSQL is authoritative, and the assignment's searchable index is updated on schedule/send transitions.
- A sender's hourly counter is reserved immediately before the SMTP attempt. A failed SMTP attempt conservatively consumes that slot until the next UTC hour, avoiding accidental over-send under retries.
- The Redis minimum-delay key is global, while the hourly counter is per tenant/sender. This is intentionally conservative when several senders are configured.
- The supplied image is a visual reference; Google and Slack integrations require valid OAuth apps and cannot authenticate until their secrets are configured.
